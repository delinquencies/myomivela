# Pet Diary audit

The homepage CTA explicitly says “See a sample diary,” but it opens an old design preview surrounded by product-looking controls. The working diary lives in Client Portal → Pet Diary. These experiences currently have different layouts, navigation, and capabilities.

| Priority | Finding | Next step |
|---|---|---|
| P0 | **The public demo looks more interactive than it is.** The sample journal has notification, interaction, and floating action buttons with no handlers. Its bottom links lead to sample service, onboarding, and Cooper pages. The alternate Scenic Route is another standalone mockup. | Replace the public journey with a clearly labeled sample rendered using the same layout as the private diary. Keep a direct Client Portal link and remove fake actions from the sample. |
| P1 | **The private feed lacks visit context.** Owners can filter updates, but an entry shows the pet, activity, publication time, notes, and optionally one photo. It does not show the visit’s status, service or summary beside the entries. The summary lives under My Bookings. Filters also include bookings without entries. | Group updates by visit and show the visit status, date, pets and completion summary together. Give active visits with no updates their own empty state. |
| P1 | **Staff capture and corrections are limited.** Staff can publish an activity only while a visit is in progress. The API accepts an update with a selected activity but no notes or photo. It exposes no correction, removal, or late-note workflow. All updates use the publication time. | Require meaningful content when the activity type needs it, distinguish activity time from publication time, and provide a correction workflow with an audit trail. |
| P1 | **Owners have to reload to see new updates.** The page fetches the feed on load and after local writes. Staff publishing in another session does not refresh the owner’s view, and there is no visible refresh action. | Start with a refresh action and a last-updated indicator. Then add foreground refresh and notifications when the delivery channel is ready. |
| P2 | **Photos and structured activity data are minimal.** One image per update at up to 2.5 MB. Walk duration, food amounts, and doses all use the same free-text field. There is no gallery and every photo uses the same alternative text. | Add activity-specific fields where they improve capture, useful captions or photo descriptions, and a visit gallery. |
| P2 | **The portal loads the whole diary.** The API returns every matching event, and filtering happens in the browser. Staff receive entries across customers. The portal diary is also English-only. | Add paginated, server-side pet and visit filtering before history grows. Translate the diary labels and activity types with the portal. |

The current API signs in the reader, scopes customer events to bookings they own, and separately checks photo access. Earlier end-to-end testing confirmed that a second customer could see neither the first customer’s diary nor its photo. This audit reviewed the current diary code and sample pages. The recommended Cloudflare Workers migration should preserve those checks when moving media to private R2.
