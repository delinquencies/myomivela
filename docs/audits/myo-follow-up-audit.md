# myo. follow-up audit

Scope: current local checkout after the navigation and pet intake changes. Findings are from code and workflow review. The earlier browser smoke test covered registration, intake, and booking. This pass reran the build, HTML validation, and JavaScript syntax check.

| Priority | Finding | Next change and acceptance check |
|---|---|---|
| P0 | **Withdrawing availability does not invalidate pending requests.** Staff can remove a window. Approval later checks for overlaps and future dates, but does not check that a published window still covers the request. See `server.mjs`, `/api/status` and `/api/slots`. | Reject confirmation if the original interval is no longer offered. Show staff a clear reason and a reschedule option. Test request → remove window → approve, and confirm that an already confirmed visit is preserved. |
| P0 | **Customers can submit incomplete care profiles.** The structured intake matches the profile, but only name and species are required. No vet/emergency contact, feeding, or allergy information is required before a request reaches staff. Empty does not distinguish “none” from “not answered.” | Decide which answers are needed by service and when. Use an explicit “none” or “not applicable” option where appropriate. Validate the agreed minimum on the server before approval or visit start. |
| P0 | **Account recovery and email verification are absent.** The application exposes registration, sign-in, and logout, but has no recovery or verification route. Booking acknowledgments appear in the portal only. | Add verified email, recovery, and booking lifecycle emails. Test delivery, expired and reused recovery links, and resend behavior. |
| P0 | **Production target is Cloudflare Workers.** The current local API uses Node HTTP, a local SQLite file, and synchronous transactions. | Port the API to a Worker and serve the public files with Workers Static Assets. Use D1 for relational data and private R2 for photos. Use an atomic database write for booking approval, including the availability and overlap checks. Test concurrent approvals, secure sessions, private media access, and database recovery in staging. |
| P1 | **Service buttons lose the customer’s selection.** Sitting, walking, and drop-in buttons all link to the same booking hash. On arrival the generic service selector defaults to the first available catalog item. | Carry a validated service selection through sign-in and pet creation. The booking form should open on the advertised service and explain when it is unavailable. |
| P1 | **The first booking flow has a dead end after intake.** From booking, the “Add a pet profile” link opens My Pets. Save refreshes that section and says “Saved,” with no next action back to the unfinished booking. | Return first-time customers to the booking step or show a “Continue booking” link after saving. Existing customers editing a profile should stay on My Pets. |
| P1 | **An empty service calendar looks like a disabled form.** The portal checks whether any slots exist globally. A selected service with no matching slots shows empty day and time controls and a disabled submit button. | Show an empty state for the selected service and provide an alternate service choice or a contact path. |
| P1 | **The intake’s last error can occur after the customer fills everything out.** Individual controls permit up to their own limits, but all fields share a 3,000-character serialized limit, including field names. The current error only tells the customer to shorten notes. | Validate a structured profile server-side with per-field limits, keep legacy notes, and show errors beside the fields that need attention. |
| P1 | **Language switches at the portal entrance.** Public pages support Spanish, while portal sign-in, intake, booking, and staff screens are English only. | Carry the language preference through sign-in and localize visible labels, server errors, dates, and notifications. |
| P1 | **Rates, service area, policies, and payments are still launch work.** The public page does not show actual catalog prices or durations, and no live payment or approved policy acceptance is wired into booking. | Approve the service area, rate card and booking terms. Show price and duration before sign-up. Publish privacy, cancellation and care authorization terms before taking real bookings or payments. |

Suggested next implementation batch: preserve the service selection, return the customer to booking after intake, and give empty calendars a useful message. In the same batch, enforce availability on approval so the improved path does not create bookings in withdrawn windows.
